# 工作原理与排坑（脱敏）

本文记录把"米家墙壁开关 → PC 关机"做出来的过程中，哪些路走得通、哪些是死路，
以及为什么最终选了"云端只读轮询锁存属性"。所有具体 did / MAC / IP / 账号名已隐去，
只保留可复用的方法与结论。

---

## 1. 触发源选型：为什么是云端轮询

智能墙壁开关常见三种无线形态，可监听性差别很大：

| 形态 | 本地可监听性 | 可行路线 |
|---|---|---|
| 经典蓝牙 BLE（广播 MiBeacon） | ✅ 能抓到并用 bindkey 解密 | 本地 BLE 被动监听（方案 B） |
| 蓝牙 MESH | ❌ 本地无可解码广播（无 bindkey，帧体过短） | 只能走云端 |
| Zigbee 子设备 | ❌ 需网关，无 token、局域网不可直读 | 基本不可行 |

本项目主力设备是 **MESH** 墙壁开关，本地这条路堵死，于是转向云端。

## 2. 云端关键发现：right-on 是"锁存翻转"

云端 miotspec 的右键开关属性（`right-on`，siid=3 / piid=1）行为是**锁存**的：
- 每按一次右键，属性在 `True/False` 间翻转；
- 翻转后**一直保持**到下一次按键，跨脚本重启、跨电脑重启都保留。

这个发现很重要，它直接决定了轮询策略：
- **慢轮询也不会漏按**（状态不会自己弹回去，3 秒读一次足够）；
- 早期用 2 秒轮询时出现过"按 3 次只抓到 1 次"的假象，后来确认是
  **多次快速翻转被慢采样混叠**，不是真的漏检。

触发逻辑因此非常简单：`当前值 != 上次值` 即一次按键；触发后立刻把基线更新为当前值（重新武装），
避免同一锁存态被反复判定为多次触发。

## 3. 左右键隔离（安全性靠结构而非测试）

miotspec 里左键走 siid=2、右键走 siid=3，是两套独立服务。脚本**只读 siid=3**，
所以左键在结构上不可能触发本链路。

> 这一点在某些场景特别重要：如果左键被接成了电脑**硬电源开关**，那么"按左键看会不会误触发"
> 这种验证方式本身就危险（会真断电）。此时应靠 **siid 隔离 + 反悔窗** 兜底，而不是物理实测左键。

## 4. 常驻监听的健壮性

一个 7×24 后台常驻的轮询脚本，最容易死在网络抖动上。关键加固：
- 把云端读调用包在 `try/except` 里，任何网络异常都当成"一次读失败"返回，
  **绝不向上抛**崩掉主循环（一次抖动只丢一次采样，下次自动恢复）；
- 连续失败到阈值（如 8 次）才判定"会话可能过期"，尝试重新登录；
- `Ctrl+C`（KeyboardInterrupt）要干净退出，不能甩一堆 traceback；
- 用 `pyw` 无窗自启时 `sys.stdout` 为 `None`，日志 handler 要做空判断，否则启动即崩。

## 5. 云端会话：扫码登录与缓存

- 登录用第三方 `token_extractor.py`（PiotrMachowski 版）的扫码连接器，server 选 `cn`；
- 登录成功后把 `userId / ssecurity / serviceToken` 缓存到 `mi_cloud_session.json`，
  之后优先用缓存，失效才重扫；
- **二维码坑**：本地二维码服务器要用 `ThreadingHTTPServer`（否则阻塞卡死）；
  二维码图片另存一份 `mi_qr.jpg` 方便手机扫；扫码等待设上限（如 120 秒）防止挂死；
  网页打不开时，退而用日志里打印的 longPolling 链接。
- **遗留风险**：无人值守时会话过期需要有人扫码。脚本会大声记日志并尝试 relogin，
  但本质上无法自动恢复——这是云端方案的固有代价。

## 6. 实测死路清单（别再试）

| 死路 | 死因 |
|---|---|
| 本地 BLE 解密 MESH 开关 | Mesh 无 bindkey，dump 帧体过短，无法解 |
| 云端事件接口（`/miotspec/event/get` 等） | 返回 `code -8`（参数无效）或 `None`，未开放 |
| 子实体（`.s3` 之类）直接读 | 回字符串或报错，拿不到稳定布尔态 |
| PyPI `micloud` 登录 | 登录步骤被拒（AccessDenied），多次无效 |
| 局域网 MIOT 读写网关守护属性 | 固件拒：`-9999 user ack timeout`（info 却正常） |
| Zigbee 子设备抓包 / 重置取 token | Zigbee 非 WiFi，抓包无意义；子设备本无 token；重置会掉配对 |
| "瞬时脉冲属性 + 慢轮询" | 若属性是瞬时态而非锁存，慢轮询必漏；本项目靠"确认锁存"才成立 |

> 教训：拿到一个设备先确认它的无线形态与云端属性是"锁存"还是"瞬时"，
> 这决定了轮询是否可行。别把设备 MAC 张冠李戴（曾把一只时钟设备的广播误认成目标开关）。

## 7. 验收方法（上线前的安全流程）

1. **先空跑**（`DRY_RUN = True`）：按键只记日志、不关机，确认每次按键都被正确捕获、
   且不会因锁存态被重复触发刷屏。
2. **再上线**（`DRY_RUN = False`）：按键 → 反悔窗倒计时 → 关机；倒计时内验证
   `shutdown /a` 与屏幕取消两条反悔通道都有效。
3. **后台自启**：用启动目录快捷方式指向 `pyw.exe <脚本>`，重启后确认进程在、日志新鲜。
4. 每次更新脚本后，用一行式校验确认机器上的文件是**新版**（旧文件残留是真发生过的事故）。
   在 GBK 控制台里，用 `py -c` 输出纯 ASCII 结论来验，比 `findstr` 可靠（`findstr` 会把
   模式里的空格当"或"，且验 UTF-8 文件会乱码）。

## 8. 反悔窗设计

任何"会关机/会执行破坏性动作"的自动化，反悔窗 **≥ 15 秒**。实测 8 秒不够——
人读完提示再点取消常常超过 8 秒，体验上像"取消了也照关"。`shutdown /s /t 15`
配合 `shutdown /a` 与屏幕取消按钮，双通道兜底。
